# Permissions

Core file: `src/lib/permissions.ts`. Client-safe constants: `src/lib/constants.ts`
(`PROGRAM_IDS`, `PROGRAM_ID_TO_LABEL`, `ACADEMIC_MENTORSHIP_PROGRAM_ALLOWLIST`).
Auth config: `src/lib/auth.ts`.

`USER_ROLES` in `src/lib/permissions.ts` is the canonical server-side role list.
Admin user create/update APIs reject unknown roles with 400 instead of silently defaulting them.

## The model — three independent axes
1. **Role** (`UserRole`): `teacher` | `program_manager` | `program_admin` | `holistic_mentorship_admin` | `admin` | `pmu_manager` | `pmu_govt_school_user` | `blended_mentor` | `blended_admin` | `alumni_manager`. The two PMU roles are pinned to JNV NVS; the two Blended Learning roles are denied everywhere except `/blended-learning`; `alumni_manager` reaches alumni only (see below).
2. **School scope** (`AccessLevel`): `1` = specific `school_codes`, `2` = `regions`, `3` = all schools. (`isAdmin` is by **role**, not level.)
3. **Program eligibility** (`program_ids`): COE=1, NODAL=2, NVS=64, plus non-JNV centre programs. Some features are gated to CoE/Nodal.

A `read_only` flag downgrades any `edit` to `view` — **including for admins**: "Admin (Read
Only)" is not a separate role, it is `role = admin` + `read_only = true` (#249). It sees every
admin surface but every admin mutation route 403s it via the `forWrite` guard option below.

## Feature access — the matrix

`getFeatureAccess(permission, feature, opts?)` returns `{ access, canView, canEdit }`:

- Looks up `FEATURE_PERMISSIONS[feature][role]` (`none`/`view`/`edit`).
- **NVS gating:** features in `NVS_GATED_FEATURES` (`visits`, `curriculum`, `pm_dashboard`, `summary_stats`, `quiz_sessions`) become `none` unless the user `hasCoEOrNodal`.
- **Academic Mentorship:** is temporarily disabled for every role by setting its feature-matrix row to `none`. The existing Program allowlist, routes, APIs, mappings, and data remain in place for later restoration.
- **Holistic Mentorship:** uses the `holistic_mentorship` feature key. Teachers, Holistic Mentorship Admins, and global Admins receive base edit access; Program Managers and Program Admins receive base view access. The shared action policy then enforces the JNV CoE (`1`), Punjab CoE (`74`), Punjab Nodal (`94`), EMRS CoE (`78`), Uttarakhand CoE (`88`), and Maharashtra Coaching Test Prep (`99`) allowlist, unambiguous Program and School scope, Teacher-seat eligibility, and Mapping ownership. Scoped managers may read program progress, Assignment Coverage, and eligible mapped or unassigned Student/Phase detail only when their resolved School/region/Centre-seat scope intersects an assigned supported Program. Their detail view exposes Profile, active Phase Guidance, and submitted Notes without draft metadata or mutation affordances; Mapping and Notes mutations, Phase configuration, and Profile regeneration remain denied. The dedicated Admin role has no other feature access.
- **Holistic Mapping lifecycle:** Teachers must name one explicit supported Program when claiming unassigned Students or removing their own Mappings; missing, null, empty, non-integer, and unsupported Program values fail before authorization or mutation. Teacher self-removal erases only that Mentor's unsubmitted draft answers for the selected Students, Program, and Academic Year in the same transaction; drafts from another Mentor, Program, or year remain untouched. Global Admins and Holistic Mentorship Admins may assign an eligible current-year unassigned Student, atomically reassign an exact active Mapping to another eligible same-School/Program Mentor, or remove an exact active Mapping after explicit confirmation and a required audit reason of at most 500 characters; `read_only` denies all three actions. A claim, Admin assignment, or stale Admin reassignment/removal returns the current Mapping ownership without changing it. After a successful Admin reassignment, the School Assignment Coverage client refreshes canonical roster ownership and keeps Mapping controls disabled until the replacement Mapping ID arrives. Admin reassignment and removal end the Mapping and erase only the outgoing Mentor's unsubmitted draft answers for that Student, Program, and Academic Year in the same transaction, while submitted Notes and unrelated drafts remain history. Admin reassignment/removal write content-free audits, and reassignment also creates the replacement Mapping in its transaction. Mapping starts, ends, and draft-erasure audits store the same normalized authenticated email and reason and use the canonical User ID only when one exists. Teacher exit, LMS access revoke, relevant app/seat-role changes, and seat loss end affected active Mappings and erase unsubmitted draft answers in the same LMS transaction; another eligible seat at the same School/Program preserves access. Canonical User hard deletion is blocked by the Holistic schema's restrictive history foreign keys; removing `user_permission` is a revoke, not a hard delete.
- **Holistic Notes authorship:** only the current Mentor may draft or Submit; submitted Notes are correctable only by their author while that author remains the current Mentor. Draft content and draft-existence metadata (state, revision, timestamp, and answer count) are returned only to the authoring current Mentor, including when the read-only override removes edit access. Every other viewer derives progress as though the draft does not exist: normally Pending, while an otherwise Skipped Phase remains Skipped, until submission creates Completed. Replacement Mentors can read submitted history and receive an editable blank form with a public revision token of `0` after an unsubmitted draft is erased.
- **Holistic Follow-up Notes (#380):** `follow_up_note_add` is a Teacher-only, Mapping-required write action. A `read_only` Teacher, Admin, Holistic Mentorship Admin, Program Manager, and Program Admin get 403; a former Mentor gets 404. Only the current Mentor may add a Follow-up Note, whoever authored the submitted Post-Session Notes, including on an applicable prior-year Grade 11 Phase. Notes are immutable (add-only) and are read by the same audience as submitted Post-Session Notes.
- **Holistic privacy erasure:** the LMS privacy-deletion endpoint and shared action policy deny every role, including global Admin. Existing immutable tombstones remain enforced by Profile regeneration, Notes writes, Historical imports, and the read-side erased-content notice; erasure is owned by the coordinated external process. Issue #412 extends the dormant helper to erase Follow-up answers and record an immutable companion audit; it grants no new permission or caller. External erasure owners must adopt the transaction contract in `patterns/holistic-privacy-erasure.md` before claiming Follow-up content is erased.
- **Staff Management Academic Mentor safeguards:** deleting a Teacher-linked permission blocks on any Academic Mentor-Mentee Mapping history; Teacher exit/revoke blocks only on active Mentees. These checks use `academic_mentorship_mentor_mentee_mappings.mentor_user_id` (`user.id`), not `user_permission.id`, and blocker messages link back to `/admin/academic-mentorship` when School/year context is available.
- **Alumni:** the `alumni` feature is `edit` for `admin` and `alumni_manager`, `none` for every other role; `read_only` can view but not save (ADR 0008, section below). Admins see it as the School page "Alumni" tab (never on centre pages; audience is physical centres only, so the tab shows only when `schoolHasAlumni` finds alumni-program students or alumni at the school, never on an NVS-only school); everyone with the feature has `/alumni` (their schools with to-add / alumni counts, `listAlumniSchools`) and `/alumni/[code]` (the same tab). `/dashboard` sends an `alumni_manager` to `/alumni`. `/alumni` also has "Find an alumnus" (`GET /api/alumni/find?q=`, `findAlumni`: AFID prefix for digits, else every name word), opening `/alumni/record/[alumniId]`. The caller's scope is applied in SQL before the LIMIT (`schoolScopeSql` in `src/lib/alumni/scope.ts`: level 3 no filter; else seat Schools, plus School codes at level 1 only or regions at level 2, matching `canAccessSchoolSync`, so leftover codes on a level-2 row don't list Schools that then 403), and `listAlumniSchools` narrows to the same scope up front. Admin → Users searches every School category (`/api/admin/schools?scope=alumni`) for an Alumni Manager, since their Punjab schools are RSMS / SoE. `canAccessAlumni` allows an alumnus with no School on record only at level 3. Routes: `/api/alumni/[alumniId]` (an existing alumnus, gated by `canAccessAlumni`); `/api/alumni/pass-out/[userId]` (a pass-out not yet added — 409 with `alumniId` once they are one) and the school-list / search routes, gated by `authorizeAlumni` (`src/lib/alumni/access.ts`: signed in → `getAlumniPermission` → `alumni` feature, edit for saves → `reachesSchool`; a pass-out with no School needs level 3). Saves go to the DB Service (`POST /alumni`, `PATCH /alumni/:id`), never Postgres. The save review (`reviewSave`, shared by the form and server) works out what applies on the record as it will be after the save (saved values plus the new non-blank ones, then `visibleValues`), checks only that, and sends only the submitted fields that still apply. So clearing one field of a blocked pair can't get past a block, a saved value that no longer applies can't block a save, and a typed value that doesn't apply isn't written. An edit must send the `version` it loaded (`alumni.updated_at`); a different one returns 409, so one person's save can't silently undo another's. An add returns 409 if someone added the alumnus meanwhile (never PATCHes their row). A save returns the new `version`, which the form sends on a quick second save; once the reload after the save lands, the form sends the reloaded record's `version` instead (someone may have saved in between). Known gap: the check runs in LMS before the write and `updated_at` has whole seconds, so it isn't atomic; that needs the DB Service PATCH to take the expected `updated_at`. Dropouts can't be added, and the profile in the response is only what the form shows. Read-only users get the form with no Save (`canEdit`).
- **`read_only` downgrade:** `edit` → `view`.

Per-row ownership uses `ownsRecord(permission, programId)` — admins own all, null program_id (unassigned) is editable by anyone with feature edit, otherwise the record's `program_id` must be in the user's programs.

Student Addition writes deliberately use a stricter gate than `ownsRecord`: admin, program admin, and program manager roles must all have the target Program in their resolved Program context. Global admins still resolve all Programs; an admin explicitly scoped only to CoE cannot edit or drop an NVS student.

## PMU roles — pinned to JNV NVS (ADR 0007, #363)

`PMU_MANAGER_ROLE`, `PMU_GOVT_SCHOOL_USER_ROLE`, `PMU_ROLES`, `isPmuRole(role)` and `PMU_PROGRAM_ID` (= 64) live in client-safe `src/lib/constants.ts`; `USER_ROLES` and `ALLOWED_STUDENT_ADDITION_ROLES` spread `PMU_ROLES`. Code outside the canonical role maps (permission matrix, labels, colours, descriptions, Dev Login personas, fixtures) uses these constants, not bare role strings (PR #376 review #5); the roster `canDropoutStudent` check reuses the exported `ALLOWED_STUDENT_ADDITION_ROLES`.

- **Matrix columns:** `pmu_manager` and `pmu_govt_school_user` get `students: "edit"` and `performance: "view"`; every other feature is `none` at every level. `read_only` makes `students` view.
- **Program context:** `getProgramContextSync` returns `{ hasAccess: true, programIds: [64], isNVSOnly: true, hasCoEOrNodal: false }` first — before admin, `scope.programs === "all"`, seat or `program_ids` logic.
- **Scope:** `resolveScope` never reads `centre_positions` for PMU roles. Level 3 → `schools: "all"` with empty `centres`/`programs`; levels 1/2 keep explicit codes / lazy regions only. So `isCentreSeated`, `getCentreConfinement` and `canAccessCentreSync` are false, and `canViewCentre` denies outright with no School fallback.
- **Ownership:** `ownsRecord` is true only for program 64 (null/unassigned is false).
- **Student narrowing:** `canAccessStudent` (view and `requireEdit`) additionally requires a current JNV NVS batch — any current batch with `program_id = 64`, not `getStudentSchool`'s `LIMIT 1` program. Student document list/upload/delete inherit this. List queries should reuse `hasCurrentNvsBatchSql(userIdColumn)` from `permissions.ts`.
- **Physical-centre features, the other direction (#434):** `isPmuOnlyStudent(studentPkId)` answers "every current batch this Student has is JNV NVS", and a route for a physical-centre-only feature 403s on it *after* `canAccessStudent`. `/api/students/[id]/exam-records` is the first user. A mixed Student (NVS plus a physical-centre Program) is not PMU-only and keeps the feature — the UI gates those on the Program the roster is acting under, so the API must not be stricter than the surface calling it. Hiding a tab is never the gate on its own.
- Visits, Curriculum, Quiz Sessions, Teacher Feedback, Summary, Holistic/Academic Mentorship, Centres, Staff Management and `/admin` are already unreachable because their guards read the matrix and program context.
- **Staff Management seats (#366):** `validateSeatOccupant` in `src/lib/staff-admin.ts` (via `rejectIneligibleSeatUser`) returns 409 when the occupant's live `user_permission` role is a PMU role, before any seat row is written (`createPosition` and `updatePosition`). The PMU check matches rows by `user_id` **or** the User's email case-insensitively (as the roster does), so an Admin-created row with no `user_id` still blocks the seat; the level-2 region rule keeps its `user_id`-only match. Seat sync never rewrites a PMU row: `syncProgramIdsFromSeats` excludes both PMU roles (with `admin` and `holistic_mentorship_admin`) via `role <> ALL($3::text[])` bound to `PROGRAM_SYNC_SKIPPED_ROLES`, and `syncAppRoleFromSeats` only moves between `teacher` and `program_manager`. The pending-Teacher/pending-PM roster only lists `teacher`/`program_manager` rows, so PMU users never show there.
- **School page (#368):** `RosterPage` returns Access Denied for a PMU role at any non-JNV School (`af_school_category !== "JNV"`), even at level 3; centre pages are denied by `canViewCentre`. At a mixed JNV School only the JNV NVS enrollment card shows (program context `[64]` ∩ programs with Students, plus NVS via `canAddStudent`). The roster is also narrowed **on the server** before any props are built (PR #376 review #1), because the "use client" `EnrollmentTabContent` only filters by the selected card: for a PMU role `RosterPage` (`scopeRosterToRole`, then `splitActiveAndDropout`) keeps only NVS Students — `studentHasCurrentProgram(s, 64)` (a current NVS batch) or `studentDroppedFromProgram(s, 64)` (an NVS dropout not undone), the same sets the NVS export lists. Active = a current NVS batch and not `status = 'dropout'`; dropout = dropped from NVS (so NVS dropouts stay undoable). The data-issues banner keeps only issues whose `groupUserId` belongs to a kept Student. CoE, Nodal and unassigned Students never reach a PMU browser. Other roles' lists and banner are unchanged. The Performance tab gets `lockedProgram = "JNV NVS"` (no program tab strip). Visits, Curriculum, Quiz Sessions, Teacher Feedback, Academic and Holistic Mentorship tabs are hidden by the matrix. `pmu_govt_school_user` never gets a back link; `pmu_manager` keeps the `hasMultipleSchools` → `/dashboard` rule.
- **Feedback / Grievance link (PR #376):** the School page header shows a "Feedback / Grievance" link to the program team's Google Form (`PMU_FEEDBACK_FORM_URL` in `src/lib/constants.ts`, new tab, `rel="noopener noreferrer"`) for PMU roles only, including `read_only`. `rosterHeaderActions` in `RosterPage` picks the header actions: Start Visit still follows `visits` edit, and PMU roles have none, so they see only the feedback link. It is a plain external link with no matrix feature or API behind it.
- **Download List for read_only PMU users (PR #376 QA):** Download List is an export (a view action). `getStudentExportAccessFromPermission` / `requireStudentExportAccess` (`src/lib/student-addition-access.ts`) run the student-addition checks (JNV School, allowed role, School scope, NVS in the program context) but need only `students` view for PMU roles; every other role still needs `students` edit. `GET /api/school/[udise]/students/export` and the Enrollment tab's `canDownloadList` (from `RosterPage`) use it, so a `read_only` PMU user keeps Download List (NVS Students only) while Add Student, Bulk Upload, edit and dropout stay hidden and 403. Existing roles are unchanged: a `read_only` admin, Program Manager or Program Admin still gets no Download List and a 403 from the export.
- **Dashboard landing (#369):** `/dashboard` sends a `pmu_govt_school_user` to `/school/<their one code>` right after the permission load, before the program-context, view, search or holistic logic (so `?view`/`?q` never stop it); a stored `school_codes` that isn't exactly one code gets the "does not have access" panel instead of a redirect loop. A `pmu_manager` is pinned to the `jnv-nvs` view (`?view=centres` ignored), the Physical Centres tab strip isn't rendered, the "JNV NVS Schools" section heading is shown (it otherwise needs PM access), and the existing single-School redirect still applies. Recent visits, the PM nav, Visit Summary and Curriculum Summary are hidden by the matrix (`pm_dashboard`/`visits`/`curriculum` = none). `resolveCentreAccess` (`src/lib/dashboard-groupings.ts`) returns no centres for either PMU role.
- **Dashboard default view (#390):** below the hard pins above (PMU, seated → Centres, Holistic Mentorship Admin, no access), an explicit valid `?view=` wins, else `getProgramContextSync(permission).hasCoEOrNodal` picks Physical Centres (true) or JNV NVS Schools (false). No access is inferred from Centre counts. A multi-School PMU Manager's School Back link is `/dashboard?view=jnv-nvs`; a PMU Govt School User still has none.
- **Planned Centre switcher (#388):** the Centre-page title switcher will reuse `resolveCentreAccess` and the destination's existing `canViewCentre` gate rather than introduce client-side authorization. Active seats confine choices to those Centres; a seatless School/region-scoped user falls back to Centres in accessible Schools; global admins see all; PMU roles see none. Only active School-linked Centres count as switchable, so School-less dashboard cards never become navigation targets. A stale list may navigate, but the destination gate must still refuse lost access. This is a grilled plan stacked on PR #394, not shipped behavior.
- **Student search and consent status (#370):** `GET /api/students/search` adds `hasCurrentNvsBatchSql("u.id")` on top of the School-scope filter for a PMU role, so a mixed School returns only NVS Students (non-NVS and unassigned ones drop out). `GET /api/schools/[code]/consent-status` now resolves permission through `getResolvedPermission` and, for a PMU role, lists and counts only Students with a current NVS batch. Other roles' SQL is unchanged.
- **Performance APIs (#371):** `authorizeSchoolAccess` now returns the resolved `permission`. The grades, batch-overview, cumulative-als, student-questions, test-questions, test-deep-dive and combined-reports (GET query and POST body) routes pass it with the requested `program` to `resolvePerformanceProgram` (`src/lib/performance-program.ts`, no DB imports). For a PMU role a missing program becomes "JNV NVS" and any other program gets 403 before any data is read; other roles get their program back unchanged. The grades route reads the caller's role and `program_ids` from `auth.permission` (no second session/permission lookup); a PMU role's program list is filtered to the pinned program (so stray CoE/Nodal ids never widen it), while other non-admin roles keep the row's `program_ids` filter. Report generation keeps `requireEdit`.
- **Combined-report session pin (PR #376 review #3):** the program pin alone lets a PMU caller name a CoE `session_id` or job id at a mixed JNV School. So `GET`/`POST combined-reports` and `GET combined-reports/[jobId]` / `POST .../retry` also call `refuseOutsidePmuSession(permission, udise, sessionId)` (`src/lib/performance-session-pin.ts`), using the job's `session_id` for the job routes. It asks BigQuery `isSessionOnlyForProgram` whether the session has JNV NVS rows and no other program's rows at that School in `fact_student_test_results_overall`. This is the table the Performance tab lists tests from; Postgres `session` rows are missing for legacy tests, and reporting jobs carry no program. No rows means refused. List/create answer 403 `Access denied`; job/retry answer 404 `Not found`, the same as another School's job. A BigQuery error is a 502 (fails closed). Other roles never trigger the lookup.
- **Session-read pin (PR #376 Codex P1):** `test-deep-dive`, `test-questions` and `student-questions` take a caller-named `sessionId`, so they share `authorizeSessionRead` (`src/lib/performance-session-request.ts`): School access, then `resolvePerformanceProgram`, then grade/`sessionId` validation, then `refusePmuSessionOr502`. That last step wraps `refuseOutsidePmuSession`: 403 unless the session is only a JNV NVS test at this School, and 502 if the BigQuery lookup fails. All of it runs before any Dynamo/BigQuery read. Other roles skip the lookup.
- **Intervention flags (PR #376 Codex P1):** `authorizeInterventionFlags` returns 403 for a PMU role at a non-JNV School, even at level 3. For PMU roles, `GET /api/schools/[code]/intervention-flags` lists only flags on the School's NVS roster (`flagStudentScopeForPmu`: `getSchoolRoster` + `studentInProgram(s, 64)`, the same set `RosterPage` keeps). Raise (`mayRaiseFlagForPmu`) and update/resolve (`mayUpdateFlagForPmu`) need a current NVS batch (`studentHasCurrentNvsBatch` / `hasCurrentNvsBatchSql`, the `canAccessStudent` rule), else the route's usual 404 ("Student not found at this school" / "Flag not found"). So a PMU user can read an NVS dropout's flags but not change them. Other roles skip these checks.
- **Curriculum Plans (#417 / #420):** `/curriculum-summary/plans`, `/plans/new`, `/plans/[id]`, `/plans/[id]/assign` and `/api/curriculum/plans/**` use the existing Admin guard (`requireCurriculumPlanAdmin` = `requireAdmin`). Reads stay bare, so a read-only Admin sees every plan page with controls disabled; every mutating handler (`POST /api/curriculum/plans`, `PATCH /api/curriculum/plans/[id]`, `PUT /api/curriculum/plans/[id]/chapters`, `POST /api/curriculum/plans/[id]/activate`, `POST /api/curriculum/plans/[id]/copy`, `PUT /api/curriculum/plans/[id]/assignments`, `PUT /api/curriculum/plans/centres/[centreId]/assignments`, `DELETE /api/curriculum/plans/[id]`) passes `{ forWrite: true }`. The Centre coverage tab (`/curriculum-summary/plans?tab=coverage`) is a bare read; read-only Admins see it with "Change plans" disabled. The assign page `/curriculum-summary/plans/[id]/assign`, `GET .../assignments` and the non-writing `POST .../assignments/preview` stay bare, so read-only Admins see the picker with checkboxes and Save disabled. PMs and program admins get 403 from the APIs and are redirected to `/dashboard` from the pages. There is no new role and no permission-matrix feature. The [Plans] button on Curriculum Summary shows beside "Manage config" for `role = admin` only (including read-only). The Admin role description in Admin user management (`ROLE_DESCRIPTIONS` in `AddUserModal.tsx`) mentions authoring Curriculum Plans.
- **Admin user management (#365):** `POST /api/admin/users` and `PATCH /api/admin/users/[id]` validate the *effective* PMU row through `resolvePmuRow` (`src/app/api/admin/users/pmu-rows.ts`); for `PATCH` that is the stored row with the body merged over it, so a role-only change is checked too. `program_ids` is always stored as `[64]` (body ignored). `pmu_govt_school_user` must be level 1 with exactly one JNV School code and no regions. `pmu_manager` level 1 needs ≥1 code, all JNV; level 2 needs ≥1 region, each with a JNV School; level 3 stores null codes and regions. Violations return 400 `{ error }`. A target with any active `centre_positions` row gets 409 (`PMU_SEATED_ERROR`, "remove their centre assignments first"); `POST` checks by email because it upserts; `PATCH` checks the `user_id` seat join and also `isSeatedEmail(stored email)` (`pmu-rows.ts`) so an email-only permission link counts as seated. In `PATCH` this PMU seat check runs before the generic seated-scope 409 ("Change their centre assignment instead"), so a seated user given a PMU role gets `PMU_SEATED_ERROR` even when the body carries `school_codes`/`regions` (review #9); non-PMU seated scope edits keep the generic message. The Admin modal shows a read-only "JNV NVS" program note, the level picker for Managers ("All JNV Schools" at level 3) and a single-School picker (a new pick replaces the old) with no level selector for Govt School Users. Switching an existing user's role to PMU Govt School User never trims their Schools (QA-11): with more than one School the modal shows an inline "must have exactly one School — remove the others" error and Save sends nothing until the Admin removes chips down to one (no School blocks Save too); switching the role back keeps the original list. The server 400 is still the backstop. `ROLE_DESCRIPTIONS`, `ROLE_LABELS` and `ROLE_COLORS` have both roles, and the user list's level-3 Level badge reads "All JNV Schools" for PMU roles ("All Schools" for everyone else).

## Blended Learning roles — deny by default (#441)

- **Roles and feature:** `blended_mentor` and `blended_admin` (client-safe `BLENDED_MENTOR_ROLE`, `BLENDED_ADMIN_ROLE`, `BLENDED_ROLES`, `isBlendedRole` in `src/lib/constants.ts`). Feature key `blended_learning` is `edit` for `blended_mentor`, `blended_admin` and `admin`, `none` for every other role; `read_only` makes it `view`. Every other feature is `none` for both Blended roles.
- **The deny-point (ADR 0008 shape, PR #415 not merged):** `getUserPermission` reads the row through the private `readPermissionRow` and returns `null` for a Blended role. So `getResolvedPermission`, `canAccessSchool`, `canAccessStudent`, `isAdmin`, `requireAdmin`/`requireAdminApiAccess` and every existing guard deny them: School pages show Access Denied, `/admin/*` pages redirect to `/dashboard` (which redirects them on), and APIs 401/403. Only Blended Learning code reads them, through `getBlendedLearningPermission(email)` (the raw row, no resolved scope). When #415 merges, its `isAlumniRole` check joins the same line.
- **Access policy (server-only):** `src/lib/blended-learning-access.ts`. `getBlendedLearningAccess(email)` returns `{ kind: "mentor" | "admin", role, readOnly, actorEmail, actorUserId, mentorUserId? }` or `null`; it requires `blended_learning` view through the matrix. An LMS `admin` resolves as a Blended Learning Admin. `actorUserId` (and a Mentor's `mentorUserId`) is `user_permission.user_id`, else the `user` row whose email matches case-insensitively, else `null`. `canBlendedLearning(access, action)`: actions `view_list`, `view_student`, `log`, `upload`, `manage_draft`, `play_recording`, `view_flags`, `view_mentors`; `log`/`upload`/`manage_draft` need `kind = "mentor"` and `!readOnly` (every Blended Learning Admin is view only); `play_recording`/`view_flags`/`view_mentors` need `kind = "admin"` (read-only admins pass). `canAccessBlendedStudent(access, studentId)` (#442) requires an active current-year Mapping (`activeBlendedMappingSql`); for a Mentor that Mapping must be to their `mentorUserId` (no Mentor user id means no Student). Call it before touching one Student. ## Alumni Manager — alumni only (ADR 0008)

- **Alumni are not Students.** An alumnus is identified by `alumni.id` and reached through the School they passed out from: `getAlumniSchool(alumniId)` (`alumni` → `student.user_id` → latest School `enrollment_record`, the same rule the alumni lists use) and `canAccessAlumni(session, alumniId, { requireEdit })`. Never use `canAccessStudent` or the `students` feature for alumni.
- **Constants:** `ALUMNI_MANAGER_ROLE` and `isAlumniRole` in client-safe `src/lib/constants.ts`; `USER_ROLES` includes it.
- **Matrix:** new feature `alumni` — `admin` and `alumni_manager` edit, every other role none. `alumni_manager` is none on every other feature. `read_only` makes it view.
- **Denied by default:** `getUserPermission` returns null for an alumni role, so `getResolvedPermission`, `canAccessSchool`, `canAccessStudent`, `isAdmin`, the dashboard and every guard built on them treat the user as having no permission. Alumni code reads the row through `getAlumniPermission` (any role, resolved scope) and must still check `getFeatureAccess(permission, "alumni")` and School scope — `canAccessAlumni` does both.
- **Scope:** level 1/2/3 with School codes or regions; `resolveScope` skips centre seats for alumni roles (`resolveSeatlessScope`, shared with PMU roles). Seating one is refused too, as for PMU roles: `rejectIneligibleSeatUser` returns 409 in Staff Management. In Admin → Users, `POST` and `PATCH` return 409 `ALUMNI_SEATED_ERROR` (`pmu-rows.ts`) when the effective role is `alumni_manager` and the person is seated (by `user_id`, or by email via `isSeatedEmail`). A seat would otherwise clear their `school_codes` and leave them with no schools.
- **Admin Users:** role option, description, label and colour added. Alumni Managers have no Programs: `POST`/`PATCH` skip the "at least one program" rule and always store `program_ids = []` (body ignored), and moving a user off the role returns 400 without `program_ids`, as for PMU roles. The modal keeps the level and School/region pickers but hides the Programs checkboxes (and so the NVS-only notice); its read-only box reads "can view alumni, cannot edit them". The user list shows "Not used" in the Programs column instead of the red "No programs". Seat-driven `program_ids` sync (`PROGRAM_SYNC_SKIPPED_ROLES`) skips the role.
- **Dev Login / tests:** `alumni_manager` Dev Login persona (`e2e-dev-alumni-manager@test.local`, seeded by `seedHolisticFixtures` at the fixture School, level 1, no Programs); e2e `TEST_USERS.alumniManager` + `alumniManagerPage`; `ALUMNI_MANAGER_SESSION` / `ALUMNI_MANAGER_PERMISSION` in `api-test-helpers.ts`.

## Scope resolution — `getResolvedPermission` vs `getUserPermission`

- `getUserPermission(email)` — bare row from `user_permission` (only `revoked_at IS NULL`), or `null` for a Blended Learning role (the deny-point above). Use for role/feature checks that don't touch school scope.
- `getResolvedPermission(email)` — `getUserPermission` **+** `resolveScope`. Use **anywhere school/centre access is actually decided** so centre seats are included. `canAccessSchoolSync` only honours seats when `scope` is populated.
- **Centre seats** (`centre_positions` → `centres` → `school`/`program`): additive. A seated user reaches that centre's school + program even with empty `school_codes`/`program_ids`. PM/SPM/PH seats at active centres also fill `scope.visitManagedSchools` (read every visit at that School, and the Visit Summary for those Schools; see `context/visits.md`). `resolveScope` degrades to explicit-only **only** on missing-schema errors (42P01/42703); any other DB error propagates (so a seated user is never silently handed an empty scope).

## The gate — what to call

- **General routes:** `getServerSession(authOptions)` → `isAdmin(email)` (admin-only) or `canAccessSchool(email, code, region?)` / `canAccessStudent(session, studentId, { requireEdit })`.
- **Admin-surface routes:** `requireAdmin` / `requireStaffAdmin` / `requireCentreAdmin` (`admin-guard.ts` family), `requireAdminApiAccess` (`api/admin/route-helpers.ts`), `requireCurriculumConfigAdmin` (`curriculum-config.ts`), and `requireCurriculumPlanAdmin` (`curriculum-plans.ts`) all take an optional `{ forWrite: true }`. **Every mutating admin handler (POST/PATCH/PUT/DELETE) must pass it** — it 403s read-only admins; reads stay bare. `isAdmin(email)` alone must not gate a write (it cannot see `read_only`).
- **School-scoped routes:** `authorizeSchoolAccess(udise, { requireEdit: true })` (`api-auth.ts`) 403s read-only callers; the success result also carries `readOnly` so list endpoints can hand the UI the same verdict (combined-report GET returns `can_generate: false, blocked_reason: "read_only"`). Report generation and retry are work, not reads — they pass `requireEdit`.
- **Academic Mentorship routes:** use `requireAcademicMentorshipAccess(session, "view"|"edit", { schoolCode? })` from `src/lib/academic-mentorship.ts`.
- **Intervention flag routes:** use `authorizeInterventionFlags(session, schoolKey)` from `src/lib/intervention-flags.ts`. Rule: anyone who can see the School's Students (School scope + `students` view) sees their flags; raising, adding notes and resolving also need `students` edit, so `read_only` accounts only view. There is no feature key. The cross-school list at `/admin/intervention-flags` is `requireAdmin` only. The Enrollment tab additionally hides all flag UI (and skips the fetch) while the JNV NVS program card is selected; this is UI only, not an API rule. **Flag deep link** (#475, used by the #470 Visit Summary School page): `/school/<code>?tab=enrollment&flag=<flagId>` makes `EnrollmentTabContent` read `flag` (`useSearchParams`) and, once the flags it already loads arrive, select the flagged Student's first non-NVS programme card and open `InterventionFlagModal` for them. ## Gotchas

- **`getUserPermission` for a school decision = bug.** Seats are absent, so a seated-but-no-explicit-codes user is wrongly denied. Use `getResolvedPermission`.
- **Raw `program_ids` for program filtering = bug.** Use `getProgramContextSync(permission).programIds` so centre-seat-derived programs are included. Otherwise a seated manager can access a school but see empty curriculum/program data for the wrong program.
- **`program_read` for a Student or configuration resource = bug.** It proves only that the actor has some supported-Program workspace scope. Bind Student reads to the exact Student/School/Program/year action, and use the dedicated Admin-only configuration read action for Phase Setup.
- **Scoping after Mapping selection = bug.** Holistic progress and filter-option queries must apply the resolved School predicate before computing first-start windows or choosing the latest yearly Mapping. Otherwise a later out-of-scope School transfer can suppress valid in-scope history or alter derived progress and exports.
- **Unscoped reconciliation before a scoped read = bug.** A current-year progress read may end stale Mappings and erase drafts before selecting rows. Pass its resolved permission into reconciliation so the write candidate set uses the same School predicate as the read result.
- **`requireEdit` matters on writes.** `canAccessStudent(session, id, { requireEdit: true })` for upload/delete — without it a `read_only` user could mutate via direct API call even though the UI hides the button. It also enforces per-program ownership in mixed schools.
- **Google-only login (ADR 0007).** Every session is a Google user whose access comes from `user_permission`. `getFeatureAccess`, `ownsRecord` and `canAccessStudent` take no session-type options, and the `next-auth` Session/JWT types carry no extra fields. Old JWTs from the retired login are rejected by `isRetiredToken`.
- **`revoked_at`** is the single "exited" switch — a revoked user resolves to no permission everywhere.
- **Postgres `bigint` columns arrive as JS strings** (no `setTypeParser` in `db.ts`). Any numeric comparison against them must cast in SQL (`::int`) or coerce (`Number()`). This bit for real in Jul 2026: `getStudentSchool` started resolving `batch.program_id` (bigint) after the #162 batch-join fix, `ownsRecord` did `[1].includes("1")` → false, and every non-admin got 403 on document upload/delete in prod for 3 days. `ownsRecord` now coerces and the query casts; keep both when touching this path.
- **School *visibility* is a separate predicate from school *access*, and it is duplicated per route.** A school is visible when `af_school_category = 'JNV'` **OR** it has an active centre (`centres c ON c.school_id = s.id AND c.is_active`). Any route resolving a school by `udise_code`/`code` must carry both halves — a JNV-only filter compiles, passes tests written against JNV fixtures, and then silently 404s the non-JNV centre schools (Punjab CoE, EMRS) whose page opens fine, so the failure surfaces as a blank widget rather than an error. This bit `consent-status` in Sep 2026: its `% Docs` pill read `—` for those schools from the day the feature shipped. Copy the predicate from `getSchoolByCode` in `src/app/school/[udise]/page.tsx`.
- **`PROGRAM_IDS` is hand-maintained** in `constants.ts` (transitional debt) — add a program id here when a non-JNV centre is onboarded.
- Import `PROGRAM_IDS` from `@/lib/constants`, not `@/lib/permissions`, in client components — `permissions.ts` pulls in the server-only DB pool.
