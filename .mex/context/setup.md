# Setup

## Prerequisites
- **Node 22** (`.nvmrc` pins it; install with `nvm install 22` then `nvm use`).
- **npm** (lockfile is `package-lock.json`).
- Access to **PostgreSQL** credentials and the **DB Service** API token (from team lead).
- Google OAuth client + (optional, per feature) BigQuery/DynamoDB/S3/SNS credentials.

## First-time Setup
1. `nvm use` (selects Node 22)
2. `npm install`
3. `cp .env.example .env.local` and fill in values (see below; ask team lead for secrets)
4. `npm run dev` → http://localhost:3000
5. In dev, log in via the **Dev Login** personas (admin / program_manager / program_admin / teacher / former_mentor / holistic_admin / read_only / pmu_manager / pmu_govt_school_user / blended_mentor / blended_admin / blended_admin_read_only / alumni_manager) — no Google needed (`src/lib/auth.ts`, only when `NODE_ENV !== "production"`). The two PMU personas are seeded by the local fixture setup at a JNV School (level 1, `program_ids = [64]`, no regions); the Alumni Manager persona at the fixture School (level 1, `program_ids = []`). The three Blended Learning personas (`e2e-blended-*@test.local`) are seeded by the same setup with level 1, no School codes, no regions and `program_ids = []`; they land on `/blended-learning`.

## Environment Variables
Required (app won't function without them):
- `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_USER`, `DATABASE_PASSWORD`, `DATABASE_NAME` — Postgres connection (reads + visit/curriculum writes). `DATABASE_SSL=false` disables SSL locally.
- `DB_SERVICE_URL`, `DB_SERVICE_TOKEN` — external write API (students/batches/quiz-sessions/documents/alumni).
- `NEXTAUTH_URL`, `NEXTAUTH_SECRET` — NextAuth (`openssl rand -base64 32` for the secret).
- `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` — Google OAuth.

Conditionally required (only if the feature is used):
- `GOOGLE_SERVICE_ACCOUNT_JSON` (or `GOOGLE_APPLICATION_CREDENTIALS`) — BigQuery quiz analytics and the Visit Summary School page's academic-level cards. The Playwright web server sets it to `" "` (a blank value would be refilled from `.env.local`), so E2E never reaches the warehouse; specs stub `/api/quiz-analytics/**` in the browser.
- `DYNAMODB_URL`, `DYNAMODB_REGION`, `DYNAMODB_ACCESS_KEY`, `DYNAMODB_SECRET_KEY` — performance dashboard.
- `S3_DOCS_BUCKET`, `S3_DOCS_PREFIX`, `S3_DOCS_REGION`, `S3_DOCS_ACCESS_KEY_ID`, `S3_DOCS_SECRET_ACCESS_KEY` — document uploads (bucket shared with prod). Blended Learning photos are uploaded (`PutObject`), checked (`HeadObject`) and presigned with them too, and Call Recordings get presigned PUTs from them (`presignUpload`). `S3_DOCS_PREFIX` must be `lms-documents`, so recording keys match the 180-day lifecycle rule and etl-next's prefixes; the bucket also needs a CORS rule allowing browser `PUT` with `Content-Type` from the LMS origins (a rollout task, not code). The Playwright web server sets fake values (`e2e-fake-docs`, `lms-documents`), so presigning works locally with no AWS traffic; specs answer `amazonaws.com` requests with `page.route`.
- `AF_ACCESS_KEY_ID`, `AF_SECRET_ACCESS_KEY`, `AF_TOPIC_ARN`, `APP_ENV` — SNS session creator. `APP_ENV` is also read by Holistic Profile regeneration, the Blended Learning wake and AI Test Insights delivery (each needs `staging` or `production`).
- `AI_TEST_INSIGHTS_ENQUEUE_URL` (AI Mentorship Guide's collection endpoint ending in `/api/internal/insight-requests`), `AI_TEST_INSIGHTS_ENQUEUE_SECRET` (bearer secret), `AI_TEST_INSIGHTS_WAKE_URL` (base URL) — AI Test Insights delivery (#550, slice #562; `src/lib/ai-test-insights-delivery.ts`). After Generate writes the request row, the LMS calls `POST {WAKE_URL}/start` (unauthenticated, failures ignored) and `POST {ENQUEUE_URL}/{request_key}/enqueue` (`Authorization: Bearer <secret>`, body `{"environment": APP_ENV}`) together, 10 s each. Generation is configured only when the enqueue URL and secret are set (blank after trimming = unset) and `APP_ENV` is `staging` or `production`; otherwise Generate answers 503 `not_configured`, writes nothing, and the card says generation is not set up in this environment. A blank wake URL only skips the wake. Deployed apps get the three from GitHub environment secrets of the same names (`Preview`, `Production`) through all three Amplify jobs and `amplify.yml`; setting the secrets is a person's setup step. Logs carry the request key, HTTP status and error name only, never the secret. The Playwright web server points all three at the **fake generator** and sets `APP_ENV=staging` explicitly (see Common Commands).
- `AI_TEST_INSIGHTS_S3_BUCKET`, `AI_TEST_INSIGHTS_S3_REGION` (default `ap-south-1`), `AI_TEST_INSIGHTS_S3_PREFIX` (default `acad-mentorship`), `AI_TEST_INSIGHTS_S3_ACCESS_KEY_ID`, `AI_TEST_INSIGHTS_S3_SECRET_ACCESS_KEY` — the AI Test Insights **artifact reader** (#550, slice #564; `src/lib/ai-test-insights-artifacts.ts`), which reads a finished AI Summary (Test Insight) from AI Mentorship Guide's bucket with its own read-only key and S3 client, separate from the `S3_DOCS_*` documents client. Reading is configured only when the bucket, key id and secret are set (blank after trimming = unset) and `APP_ENV` is `staging` or `production`; otherwise the summary route answers 503 `not_configured` and the card shows "The AI Summary could not be loaded" with Retry. A blank region or prefix uses its default. All environments share one bucket: the reader only reads a key under `{PREFIX}/{APP_ENV}/items/{item id}/`. Deployed apps get the five from GitHub environment secrets of the same names (`Preview`, `Production`) through all three Amplify jobs and `amplify.yml`; creating the read-only key and setting the secrets is a person's setup step. `AI_TEST_INSIGHTS_S3_ENDPOINT` is **local only** (the fake generator's object store; path-style addressing): the deploy workflow never passes it, so a deployed app can never set it. Logs carry the request key, `student.id`, a reason and an error name, never the text or an S3 key. The Playwright web server points all six at the fake generator.
- `BLENDED_LEARNING_SES_ACCESS_KEY_ID`, `BLENDED_LEARNING_SES_SECRET_ACCESS_KEY`, `BLENDED_LEARNING_SES_REGION` (default `ap-south-1`), `BLENDED_LEARNING_WELLBEING_EMAILS` (comma-separated; `shalinijha@` in production) — the well-being email sent after a Conversation with an Emotional Well-being Mentor Flag is saved (`src/lib/blended-learning-wellbeing-notifier.ts`, `af-lms-ses` IAM user, from `no-reply@avantifellows.org`). The link uses `NEXTAUTH_URL`. If the key id, secret or recipients are unset, the email is skipped without error. The Playwright web server sets the key id and recipients to `" "` (a blank value would be refilled from `.env.local`), so e2e never sends.
- `BLENDED_LEARNING_ETL_URL` (the etl-next base URL, no path), `BLENDED_LEARNING_ETL_TOKEN` (machine token bound to `APP_ENV`) — the wake call after a Call Recording upload creates a Conversation Draft (`wakeTranscription` in `src/lib/blended-learning-drafts.ts`): `POST {URL}/api/internal/blended-learning/transcription-requests/{request_key}/enqueue` with `{"environment": APP_ENV}`. If the URL or token is unset (blank after trimming) or `APP_ENV` is not `staging`/`production`, the wake is skipped without error and the draft stays `transcribing`. The Playwright web server sets both to `" "`, so e2e never calls etl-next.

- `HOLISTIC_DICTATION_ENABLED`, `HOLISTIC_DICTATION_ELEVENLABS_API_KEY`, `HOLISTIC_DICTATION_ELEVENLABS_ZERO_RETENTION`, `HOLISTIC_DICTATION_OPENROUTER_API_KEY`, `HOLISTIC_DICTATION_TRANSLATION_MODEL` — Holistic Dictation (#500), server-only. Dictation is on only when the flag is `true` and both keys are set (the OpenRouter key translates non-English transcripts into English, ADR 0013). `HOLISTIC_DICTATION_TRANSLATION_MODEL` is optional: blank or unset uses `openai/gpt-6.1-terra`, and a replacement model must support reasoning off. Deployed apps get them from the GitHub environment secrets of the same names (`Preview` for staging, `Production`): every Amplify job in `.github/workflows/deploy-amplify.yml` syncs them and `amplify.yml` writes them into `.env.production`. A secret that isn't set arrives blank, which leaves Dictation off (or, for the model, uses the default). A new setting that is missing from the workflow is wiped on every deploy, because each job replaces the branch's whole variable set. The Playwright web server sets the flag on; `holistic-mentorship.spec.ts` fakes the dictation route with `page.route` in most tests, and the server-side preload (below) fakes both providers, so neither ElevenLabs nor OpenRouter is called. The page reads today's usage from `holistic_mentorship_dictation_usage_records`, which e2e gets from the `*holistic*.exs` migration in `../db-service_holistic_mentorship` (db-service #858; check the checkout has `20261110151931_create_holistic_mentorship_dictation_usage_records.exs` and `20261116113700_add_translation_to_holistic_dictation_usage_records.exs`, since the LMS writes the `detected_language` and `translation` columns). The spec also fakes `getUserMedia` and `MediaRecorder` with an init script: headless Chromium's `--use-fake-device-for-media-stream` (and even Web Audio) stalled on macOS, so the browser's audio stack is not used.

Never commit real values — `.env.local` is gitignored; CI injects prod/preview values via the Amplify workflow.

## Common Commands
- `npm run dev` — dev server on :3000 (hot reload).
- `npm test` / `npm run test:unit` — full Vitest run; `npm run test:unit:watch` for watch; `npm run test:unit:coverage` for coverage.
- `npm run test:e2e` — Playwright E2E (`:ui`/`:headed` variants exist).
  Global setup runs db-service migrations with `mix` from `../db-service_holistic_mentorship` (hard-coded in `e2e/helpers/db.ts`). If that checkout is absent, holistic tables are on `db-service` main, so a temporary symlink to `../db-service` works. With asdf and no `.tool-versions`, put `~/.asdf/installs/elixir/<ver>/bin` and `~/.asdf/installs/erlang/<ver>/bin` on `PATH` directly. The web server preloads a provider fake from `e2e/helpers/` through `NODE_OPTIONS` (set in `playwright.config.ts`): the e2e preload fakes both providers (ElevenLabs Scribe and the OpenRouter translation) with fixed replies from `e2e/helpers/fake-providers.json`, refuses any other request to those hosts, and is the only thing that sets the dummy Dictation keys, so a server without it has Dictation off. By default Scribe hears English and the translation succeeds; a spec steers the next calls (Hindi, a failing translation) with `steerFakeProviders`, which writes a small control file in the temp directory that the fake reads on each call, and the Holistic spec removes it after every test. This relies on e2e running one test at a time (`workers: 1`).
- `npm run fake:ai-mentorship-guide` — starts the AI Test Insights **fake generator** (`e2e/helpers/fake-ai-mentorship-guide.cjs`, not shipped) on `127.0.0.1:3051` (`FAKE_AI_MENTORSHIP_GUIDE_PORT` overrides) for local QA. Point the app at it with `AI_TEST_INSIGHTS_ENQUEUE_URL=http://127.0.0.1:3051/api/internal/insight-requests`, `AI_TEST_INSIGHTS_WAKE_URL=http://127.0.0.1:3051/wake`, the secret from `e2e/helpers/fake-ai-mentorship-guide.json` and `APP_ENV=staging`. It answers the wake call (202) and the enqueue call (503 asleep, 401 bad bearer, 422 body not exactly `{"environment":"staging"}`, else the steered 202 / 401 / 404 / 422); `POST /__fake/steer`, `GET /__fake/calls` and `POST /__fake/reset` steer and inspect it (specs use the helpers in `e2e/helpers/fake-ai-mentorship-guide.ts`). It logs no text. Its database side (#563) needs `DATABASE_HOST` (default `localhost`), `DATABASE_PORT`, `DATABASE_USER`, `DATABASE_PASSWORD` and `DATABASE_NAME` (it does not read `.env.local`), and it refuses to start for any host other than localhost, a missing `DATABASE_NAME`, or `dbservice_test_ati550_real` (QA uses a clone). Steered with `{"enqueue": "accept", "run": "hold" | "no_data" | "failed", "outcomeCode"}` it claims an accepted request after the 202 (`queued` → `running`, `started_at`) and holds or ends it; `POST /__fake/end` ends a held one. Steered with `"run": "complete"` (or `POST /__fake/end {"requestKey", "state": "completed"}`), it completes the request as AI Mentorship Guide does (#564): in one transaction a Session (`config_snapshot_json` `{"fake_ai_mentorship_guide":true}`, which e2e cleanup uses), an Item for the request's Student, two Item File rows (`report` at `output/final-report.md`, `report_pdf` at `output/report.pdf`, keys `acad-mentorship/staging/items/{item id}/…`) and the request `completed` with that Item, guarded by `state IN ('queued', 'running')`, all times UTC. It serves those files as a local object store at `GET /{bucket}/{key}` (path-style; only keys an Item File row of its environment holds in that Item's folder, signed with its read-only key id; 404 `NoSuchKey` / 403 `AccessDenied` otherwise). The bytes come from `e2e/helpers/fake-ai-test-insight.json` (the fixed Markdown, with a table, and a small PDF), which the spec reads too. Accepted without `run`, a request stays `queued` (steered mode, the default, for specs). `npm run fake:ai-mentorship-guide:auto` starts it in **auto mode** for local QA: every accepted request is claimed at once and completed `autoCompleteAfterMs` (5 s) later, and on start it picks up the `queued` rows already in the database. For QA also point the app's reader at it: `AI_TEST_INSIGHTS_S3_ENDPOINT=http://127.0.0.1:3051` and the `store` bucket, prefix, key id and secret from `fake-ai-mentorship-guide.json`. Playwright starts it as a second `webServer` beside `next dev` (steered); the AI Test Insights spec resets it around its delivery tests.
- `npm run lint` — ESLint (`eslint-config-next`).
- `npm run build` — production Next build.
- `npm run fallow:health` — codebase health/hotspots; `fallow:dead-code`, `fallow:audit` for cleanup/PR risk.
  - `package.json` pins fallow to one exact version (3.43.2, no `^`), so `npm ci` and the CI Fallow job install the same one; the CI log line "Installed fallow …" confirms it. Upgrade deliberately: change that version and the lock file in one PR, and move `uses: fallow-rs/fallow@vN` in `.github/workflows/fallow.yml` with the major. (Until 2026-11-18 the spec was `^2.96.0`: the lock file kept laptops on 2.96.0 while CI installed the newest 2.x, 2.104.0, which scored differently and failed PR #533 after it had passed locally.) Fallow counts React hook density toward cognitive complexity, with a threshold of 15. To reproduce the CI gate, run `npm ci`, `npm run test:unit:coverage`, then `npx fallow audit --base origin/main --coverage unit-coverage/coverage-final.json`. Restore the tracked `coverage/coverage-summary.json` afterwards. On a busy machine pass `-- --testTimeout=30000` to the coverage run so slow component tests don't time out. Untested page components and server functions score CRAP = cyclomatic² + cyclomatic, so any function with cyclomatic ≥ 5 needs unit coverage or a split (scripts outside `src/` are never covered, so keep them thin and move logic into tested `src/lib` modules).
  - The audit diffs the PR merge ref against the PR's *old* merge-base, so findings merged into `main` by another PR show up as "changed files" on yours. Merge `main` into the branch to move the base forward, and reproduce with `--base <old merge-base>`. Editing a file makes fallow treat its existing high-CRAP functions as new, so budget for tests on the whole file. A component's prop count also adds to its cognitive score (about one point per prop past four), so a 19-prop component fails on props alone; pass a pre-rendered slot (`actions: ReactNode`) instead of forwarding props. `--format json --complexity-breakdown` on `fallow health` lists each contribution.
- Data scripts (one-off, via `ts-node`): `npm run centres:import`, `npm run blended:import-links` (Profile Doc / Screener Links; `patterns/load-blended-learning-links.md`), `npm run pm:import`, `npm run db:setup-permissions`, etc. (see `scripts/`).
- `npm run curriculum:seed-plans -- <workbook.xlsx>` dry-runs the one-time 2026-27 Curriculum Plan seed (#417 / #425) and prints the report; add `--apply` to create the three Draft plans in one transaction (all or none; `createCurriculumPlanDrafts` in `src/lib/curriculum-plans.ts`). Argument parsing lives in `src/lib/curriculum-plan-seed-args.ts` and the database side in `src/lib/curriculum-plan-seed-store.ts`. Needs the db-service plan tables; locally, apply `e2e/fixtures/migrations/20261019120000_add_lms_curriculum_plans.sql` to a throwaway DB clone rather than `dbservice_dev`. The workbook is never committed.
- Holistic release setup: `npm run holistic:setup-local -- --confirm-synthetic-database --program-id=<1|74|94|78|88|99>` applies the sibling DB Service migrations and synthetic fixtures to a local-only database. Production preflight requires `--historical-source=<private-json>` for Program 1, uses it for a Program 78 Historical run when applicable, and omits it for live Programs 74, 94, 88, and 99. Follow `docs/holistic-mentorship-release.md` for the separate commands, staging order, sign-off, monitoring, and rollback.

## Common Issues
- **Port 3000 in use:** `lsof -i :3000` then `kill -9 <PID>`.
- **`undefined_table`/`undefined_column` (42P01/42703):** the connected DB is missing a migration (e.g. centre-seat schema). The DB schema is owned by the DB Service repo — apply its migrations, don't add columns here.
- **DB Service writes 401/4xx:** check `DB_SERVICE_URL`/`DB_SERVICE_TOKEN`; the proxy route surfaces the upstream error text in `warnings`/`error`.
- **Pool exhaustion / hung queries:** `src/lib/db.ts` caps at 10 connections with 15s `statement_timeout`; a leaking caller shows as `connectionTimeoutMillis` errors after 5s.
- **Knowledge graph (`graphify-out/`) out of date:** it's regenerated locally and not committed — run `/graphify --update` to refresh it against the current code (AST refresh is free; only changed docs cost tokens).
