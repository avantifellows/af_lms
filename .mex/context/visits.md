# PM School Visits

A Program Manager (PM) or Program Admin opens a visit at an in-scope school, performs
one or more typed "actions" (interactions/observations), then completes the visit. GPS is captured at start/end.
Visit rows are LMS-owned and written **directly to Postgres** (not the DB Service).

Completion requirements are role-aware: PMs need completed Actions for all six mandatory Action Types
(all except School Staff Interaction), including a rubric-valid Classroom Observation. Admins may complete
any in-scope Visit and Program Admins may complete their own Visit with zero Actions. Every role still needs
valid end GPS and cannot complete while a non-deleted Action is in progress; repeat completion returns the
stored completion state without changing its GPS or timestamp.

## DB tables
- **`lms_pm_school_visits`** — 2-state lifecycle: `in_progress` → `completed` (`completed_at`). Holds `school_code`, `pm_email`, `visit_date` (derived server-side as IST date), start/end GPS columns, `deleted_at` soft delete. No `data` column, no `ended_at`. Ecto timestamps.
- **`lms_pm_school_visit_actions`** — one row per action: `action_type`, `status` (`pending`/`in_progress`/`completed`), start/end GPS+timestamps, `data` JSONB (the type-specific payload), `deleted_at`.
- Action types are enforced in **app code** (`ACTION_TYPES` in `src/lib/visit-actions.ts`), not a DB CHECK.

## Access layer — `src/lib/visits-policy.ts` (NOT raw permissions)
Visit routes do **not** call `canAccessSchool` directly. They use:
- `requireVisitsAccess(session, "view"|"edit")` → `{ ok, actor }` or `{ ok:false, response }`. Resolves the permission, checks the `visits` feature.
- `enforceVisitReadAccess` / `enforceVisitWriteAccess(actor, target)` — per-visit ownership: a **program_manager** edits only their own visits (`pm_email` match) and reads their own plus every visit at a **visit-managed School** (below); **admin** has scoped read/write; **program_admin** has scoped read access and edits only their own in-progress visits.
- **Visit-managed Schools (#291):** a Centre seat in `VISIT_MANAGER_SEAT_ROLES` (`pm`, `spm`, `ph`; `src/lib/staff-shared.ts`) at an **active** Centre (`centres.is_active`) makes that Centre's School visit-managed. Visits carry a School, not a Centre, so at a School with both a CoE and a Nodal centre a manager of either sees all its visits — intentional (Pritam, 14 Oct 2026): a PM's trip covers both centres' people. `resolveScope` collects them into `scope.visitManagedSchools`; `managesVisitSchool(actor, code)` reads it. The holder reads **every** visit there, whoever made it — read-only, never edit/complete/delete. APM and teaching seats give no visit visibility beyond their own. No reporting hierarchy is stored; Centre seats are the whole rule. A bare `getUserPermission` has no scope and manages nothing. They also get the Visit Summary (`/school-visit-summary` and `[id]`; `canViewVisitSummary`), scoped by `buildVisitSummaryScopePredicate` to the managed Schools **only** — not their own visits elsewhere. A `program_manager` with no managed School is still redirected to `/visits`.
- `buildOwnOrManagedVisitPredicate(actor, opts)` — the program_manager list scope (`LOWER(TRIM(pm_email)) = $n` OR `school_code = ANY(managed)`), used by `/visits`, `GET /api/pm/visits` (School Visit History tab) and the dashboard. Those lists name the visitor and offer only View (no Continue/Delete) on someone else's visit; `GET /api/pm/visits` returns `can_edit` per row (feature edit AND `canEditVisit`) for the School Visit History tab. Dashboard Recent Visits sorts the user's own in-progress visits first, so other people's stale ones can't push them out.
- `enforceVisitWriteLock(status)` — returns 409 if the visit is `completed` (completed visits are read-only; only `admin` may edit completed action *data*, via `canEditCompletedActionData`).
- `buildVisitScopePredicate(actor, opts)` — SQL `WHERE` fragment to scope list queries (handles level 1/2/3 + seat schools).
- `apiError(status, error, details?)` — the standard structured error response for these routes.

Visit pages that gate entry before calling an API must also use `getResolvedPermission`; a bare
`getUserPermission` omits Centre-seat-derived schools and programs. In particular, the new-Visit
page uses the resolved permission for its Visits feature check before rendering the form.

Role semantics: **PM owner** = read/write own, plus read-only on every visit at their visit-managed Schools; **admin** = scoped read/write; **program_admin** = scoped read plus write on owned in-progress Visits. `read_only` downgrades every role to view-only, and Visit/Action pages combine feature-level `canEdit` with the ownership policy before rendering mutation controls.

## GPS — `src/lib/geo-validation.ts`
`validateGpsReading(body, "start"|"end")` reads `${prefix}_lat/_lng/_accuracy`. Rejects (422) accuracy > 500m or out-of-range lat/lng; warns (still accepts) between 100–500m. **Never log lat/lng.** Routes that need GPS: create visit, action start, action end, complete visit.

## The action-type registry (7 types)
Types: `principal_interaction`, `classroom_observation`, `group_student_discussion`,
`individual_student_discussion`, `af_team_interaction`, `individual_af_teacher_interaction`,
`school_staff_interaction` (the only one in `OPTIONAL_ACTION_TYPE_VALUES`).

Each type is implemented across coordinated files:
- **`src/lib/<type>.ts`** — the config constant (`<TYPE>_CONFIG`: sections/questions or rubric), the `<Type>Data` interface, `validate<Type>Save` + `validate<Type>Complete` (both return `{ valid, errors }`; save = looser, complete = full completeness), plus `extractRemarks` + `computeInlineStats` for the summary view.
- **`src/components/visits/<Type>Form.tsx`** — the form, rendered via `ActionDetailForm.tsx` which dispatches on `action_type`. The form component owns the `data` payload shape — there is **no** per-type bootstrap/sanitize function.
- **Shared helpers** — `src/lib/visit-form-utils.ts`: `isPlainObject` plus the `additional_notes` helpers (`readActionAdditionalNotes`, `appendActionAdditionalNotes`, `validateActionAdditionalNotes`). Validators read the JSONB `data` directly.
- **Registration** — entry in `ACTION_TYPES` (`src/lib/visit-actions.ts`); the summary stats + label are wired in `ActionPointList.tsx`, which calls each type's `computeInlineStats`/`extractRemarks`.

Most types follow the **binary-question checklist** shape (`RadioPair` yes/no + optional remark per question); classroom observation uses a versioned **rubric** (`getRubricConfig`, `CURRENT_RUBRIC_VERSION`, `computeTotalScore`). Teacher-fetching forms pull from `/api/pm/teachers`, backed by `getVisitTeachersForSchool`: active real AF teachers with active LMS permissions and active teacher-type Centre seats at active Centres linked to the Visit's School. There is no fallback to broad `user_permission.role = 'teacher'` scope.

**Naming exception:** validator names mirror the type key, *except* `individual_af_teacher_interaction`, whose validators are `validateIndividualTeacherSave`/`validateIndividualTeacherComplete` (no "AF").

## Visitor display name
Visits store only `pm_email`. Wherever a visitor's name is shown (the School page Visit History tab via
`GET /api/pm/visits`, and the Visit Summary page), it is resolved from `user_permission.full_name` by
case-insensitive email match, falling back to the email when no name exists. The list API uses a
**scalar subquery** (preferring the non-revoked row) rather than a `LEFT JOIN user_permission`.
`user_permission.email` is unique only case-sensitively (`user_permission_email_index`), so a case variant of
the same address can exist as a second row and a case-insensitive join would duplicate visits. Visit History renders it as
"Visited by <name>" with the email as the hover title.

## Gotchas
- Use **`visits-policy` helpers**, not `permissions.ts` directly, in visit routes — they encode PM and Program Admin ownership plus Admin scope semantics.
- **Save vs complete** validation are different functions — a draft can save with gaps; complete demands full data.
- Completed visits are write-locked (`enforceVisitWriteLock`); only `admin` edits completed action data.
- Adding a type means touching ~8 files in lockstep — follow `patterns/add-visit-action-type.md`, and note `school_staff_interaction` is optional so completeness/aggregate code must tolerate its absence.

**Visit Summary scope (#470 slice #474, built):** every `/school-visit-summary` query (the Visits list, its six stat cards and the School/PM filter options) builds its `WHERE` in the shared server-only module `src/lib/visit-summary-scope.ts` — `normalizeVisitSummaryFilters(searchParams)`, `buildVisitSummaryWhere(actor, filters, { startIndex?, exclude? })` (`exclude: "regions" | "schools" | "pms"` drops an option list's own filter) and `getVisitSummaryRegionOptions` / `getVisitSummarySchoolOptions` / `getVisitSummaryPmOptions`. The caller aliases the Visit as `v` and LEFT JOINs `school s ON s.code = v.school_code` (region scope reads `s.region`). The module always adds the **physical-only** predicate: `EXISTS` an `is_physical AND is_active` Centre at the Visit's School (`school.code` → `centres.school_id`). That rule plus the actor's summary scope is one exported helper, `buildVisitSummarySchoolPredicate(actor, { startIndex, schoolCodeColumn, schoolRegionColumn })`; `buildVisitSummaryWhere`, the School page lookup and the concern-events API lookup all use it, so never re-type it inline. A Visit at a School with only a JNV NVS Centre, or whose only physical Centre is inactive, is absent from the table, every stat card and both option lists; a mixed JNV (physical + NVS Centre) still shows. The gate is unchanged (`visits` view + `canViewVisitSummary`, rows scoped by `buildVisitSummaryScopePredicate` inside the module). The visit detail page `/school-visit-summary/[id]` does **not** use the module and still shows any in-scope Visit. Its "Back to Visit Summary" goes to `visitSummaryBackHref(back)` (`src/lib/visit-summary.ts`): the `back=` param when it is `/school-visit-summary[?…]` or `/school-visit-summary/schools/<code>[?…]` (no open redirect), else `/school-visit-summary?tab=visits` (School-wise is the default tab, so a bare link would land there). **Page gate:** the list, the School page and the visit detail page all start with `requireVisitSummaryPage()` (`src/lib/visit-summary-page.ts`, server-only): no session → `/`; no permission row or no `visits` view → `/dashboard`; `canViewVisitSummary` false → `/visits` for a PM, else `/dashboard`; returns `{ actor, visitsAccess }`. Links that carry the current params use `searchParamsWithout(current, omitKeys, initial?)` in `src/lib/visit-summary.ts` (the filter bar still has its own copy), and IST display goes through `formatIstDate` / `formatIstTimestamp` / `formatVisitCount` there (client-safe; no local copies). Later #470 slices must read Visits in view through this module.

**Region filter (#470 slice #476, built):** `regions=` is a comma list on `school.region`, like `schools=`/`pms=`. The sentinel `__none__` matches `school.region IS NULL` (non-JNV Schools) and is offered as **"No region (non-JNV)"**; named regions and the sentinel combine with OR. An unknown region just matches nothing. Region options are the distinct `s.region` of the Visits in view under every other filter (exclude-own-filter, as School and PM). The filter bar order is Region, School, PM, Status, Required Completion, Date Preset, From, To (one row at `xl`). **Tabs and the School-wise tab (#470 slice #477, built):** `/school-visit-summary` has two tabs (`SummaryTabs` in the page): **School-wise** first and default (`tab=schools`, a missing or unknown `tab`) and **Visits** (`tab=visits`; its table, six stat cards, sort and 20-row pagination unchanged). Both share the filter bar; its "Clear filters" keeps `tab`, `sort` and `dir`. Tab links keep every filter param and drop `sort`, `dir` and `page`. **`sort`/`dir` are interpreted per tab**: each tab has its own whitelist (Visits: `SORT_COLUMNS` in the page; School-wise: `SCHOOL_WISE_SORT_COLUMNS` in `src/lib/visit-concerns.ts`, renamed from `visit-summary-school-wise.ts` in #478), and a key from the other tab or anything unknown falls back to that tab's default (Visits `visit_date desc`, School-wise `recurring desc` since #478); a bad `dir` falls back to the key's default direction. School-wise rows come from `getSchoolWiseView(actor, filters, sort)` (server-only), which groups the Visits in view from `buildVisitSummaryWhere` by School: one row per School with ≥ 1 Visit in view, any status. Columns School (region) · Visits · Last visit; sort keys `school_name` (asc), `visits` (desc), `last_visit` (desc), every tie broken by school name. No pagination. Stat cards: Schools · Visits (sum of the rows). Last visit shows **Stale** when it is more than `STALE_LAST_VISIT_DAYS` (45) days before today in IST (`isStaleLastVisit` in `src/lib/visit-summary.ts`; exactly 45 days is not stale). **Visit Concerns read model and Recurring Concerns (#470 slice #478, built):** `src/lib/visit-concerns.ts` (server-only) owns **every** read of `lms_visit_concerns` / `lms_visit_concern_mentions` / `lms_visit_concern_events` / `lms_visit_note_summaries`; the School page slices extend it with `getSchoolConcernPage`. It reads Visits in view only through `buildVisitSummaryWhere`. **Live mention rule:** a mention counts only when its Visit is `completed` and `deleted_at IS NULL` (deleted Visits are never in view, so a soft-deleted Visit stops counting with no write); a record with no live mention in view is hidden. `getSchoolWiseView(actor, filters, sort)` returns `{ stats, freshness, rows }` from one CTE query plus a freshness query: `visitCount` = distinct live-mention Visits in view (same-day Visits count separately); **Recurring** = `kind = 'concern' AND status = 'open'` with `visitCount >= RECURRING_CONCERN_MIN_VISITS` (2; exported from `src/lib/visit-summary.ts`, bound as a `$n` parameter in the SQL and read by the School page's "Recurring ·" label); `openCount` = open concerns with ≥ 1 live mention in view; resolved concerns and highlights never count. Top recurring concern = highest `visitCount`, then latest mention `visit_date`, then lowest id. Columns: School (region, with a severity marker from `concernSeverity` in `src/lib/visit-summary.ts`: ≥ 3 recurring / 1–2 / 0 recurring but open > 0 / open 0) · Visits · Last visit · Recurring issues (sort key `recurring`, the default, desc; ties by school name) · Top recurring concern (text rendered as plain text, clamped to 2 lines, "N visits" beneath; not sortable; "—" when none). Stat cards Schools · Visits · Schools with recurring concerns · Open concerns. **`recurring=1`** ("Recurring concerns only", a checkbox in the filter bar header shown on the School-wise tab only) is `filters.recurringOnly` in `normalizeVisitSummaryFilters`; `buildVisitSummaryWhere` ignores it (not a Visit filter) and the read model drops rows with `recurringCount = 0`; the stat cards and "N schools found" follow the rows kept; tab links keep it. **Freshness line** under the stat cards: "Visit notes summarised up to <MAX(summarised_at), IST> · N visits waiting" (`summarised_at` is UTC `timestamp without time zone`, read `AT TIME ZONE 'UTC'`; waiting = completed Visits in view with no summary row, counted per School in the rows query and summed over the rows kept, so with `recurring=1` it counts only the Schools still listed (product decision on review finding #6, 28 Oct 2026); the freshness query reads only `MAX(summarised_at)`; edited-but-not-re-summarised Visits are not counted), or "Visit notes haven't been summarised yet" when the summaries table is empty (Schools still list, with 0 concerns). **Deploy order:** the tables come from a db-service migration that did not exist yet when this was built (27 Oct 2026); that migration must be in **prod before this ships**, or every School-wise query fails with "relation does not exist". E2E mirrors the four tables and the append-only trigger in `e2e/fixtures/migrations/20261027140000_add_lms_visit_concerns.sql` (from PRD §1; re-diff against the db-service migration when it lands) and seeds the concern fixture in `20261027140100_seed_visit_concerns_fixture.sql` (its header lists the hand-worked answers).

**Concern Resolution writes (#470 slice #482, built):** managers who are not read-only can **resolve** an open Visit Concern (Concern Resolution), **comment** on a resolved one, or **reopen** a resolved one with a reason. History is append-only (the events table's trigger refuses UPDATE/DELETE). **Write module** `src/lib/visit-concern-events.ts` (server-only): `resolveConcern` / `commentOnConcern` / `reopenConcern(client, { concernId, actorEmail, body })`, each run inside `withTransaction`: `SELECT kind, status … FOR UPDATE` the concern, refuse a highlight or the wrong status (`VisitConcernEventError` 409), `UPDATE status, updated_at` (resolve → `resolved`, reopen → `open`; comment leaves the row alone), `INSERT` one `lms_visit_concern_events` row (`resolved` / `comment` / `reopened`, trimmed body, lower-cased `author_email`, `inserted_at = NOW() AT TIME ZONE 'UTC'`). Direct Postgres is right here: these are LMS-owned history tables like the intervention-flag history; the DB Service write rule doesn't apply (pattern `patterns/lms-owned-history-write.md`). db-service's auto-reopen locks the same row. **Route** `POST /api/visit-concerns/[id]/events` with `{ action: "resolve" | "comment" | "reopen", body }`, checked in this order: no session → 401; `requireVisitsAccess(session, "edit")` fails (incl. `read_only`) or `canViewVisitSummary` false → 403; non-integer id, unknown action, body not a string or trimmed length outside 1–2000 → 400; `findVisitSummaryConcern(actor, id)` (in the read model) finds nothing — missing, School outside `buildVisitSummaryScopePredicate`, no active physical Centre, or no live mention → 404 "Concern not found"; highlight, resolve on resolved, comment/reopen on open → 409; success → 201 `{ ok: true }` (the client only checks `res.ok` and calls `router.refresh()`, so nothing is read back after the write). Client-safe limits and action names live in `src/lib/visit-concern-event-types.ts`. **UI:** the School page passes `canAct = getFeatureAccess(permission, "visits").canEdit` to `SchoolConcernSections`, which renders the client `src/components/visits/ConcernActions.tsx` on each card: Resolve on Needs attention cards ("How was this resolved?"), Comment and Reopen ("Why is this being reopened?") on Resolved cards (layout: "School page layout" below). It trims and checks 1–2000 chars before posting, shows "Saving…", on failure shows the API error (`role="alert"`) and keeps the typed text, on success calls `router.refresh()` so the card moves section. Read-only users see concerns and history with no controls.
